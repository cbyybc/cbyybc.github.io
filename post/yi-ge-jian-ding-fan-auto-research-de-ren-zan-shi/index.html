一个坚定反auto-research的人（暂时）

2026-11-09 5 min read

我在一个对话里，把 Codex 养成了一坨屎山

事情的起因其实非常简单。

我正在做一个项目，需要调用大模型的 API 完成一次实验。之前已经有类似的代码，所以我想着让 Codex 稍微修改一下，应该很快就能搞定。

结果，这件事折腾了我大半天，最后几乎让我崩溃。

一、一切从一个报错开始

最开始，我让 ChatGPT 帮我写了一份比较完整的 Prompt，交给 Codex 执行。

Codex 的表现相当认真。不仅完成了功能，还设计了实验记录、错误处理、预算控制、自动验证等机制。几百项测试全部通过，历史文件也做了完整性检查。

看起来非常专业。

然后我运行程序，报错了。

我把错误发给 ChatGPT，它分析了一下，认为现有程序缺少某种保护机制，于是又给了我一份 Prompt，让 Codex 继续完善。

Codex 照做了。

再运行，又报错。

于是继续分析，继续修改。

起初我并没有觉得有什么问题，毕竟程序出错，修复 Bug 是很正常的事情。

但我后来发现，我们始终在原来的设计上增加东西，却从来没有认真考虑过这个设计本身是不是有问题。

二、一个越来越无法运行的系统

接下来的过程，基本变成了一个循环：

报错 → ChatGPT 分析 → 生成新 Prompt → Codex 增加保护机制 → 测试通过 → 再次报错。

从 API 请求异常开始，代码逐渐加入了费用审计、账户隔离、身份绑定、权限核验、人工审核收据、锁内预检查等一整套机制。

每一次修改，单独看似乎都有道理。

ChatGPT 总能找到一个合理的解释，Codex 也会认真执行，尽可能把所有异常情况考虑进去。

最后，项目里出现了好几套控制器、越来越复杂的账户状态和审计文件，以及将近九百项通过的测试。

但我最开始想做的那个实验，依然一次都没有成功运行。

最荒诞的地方在于，程序已经可以非常可靠地告诉我为什么不能运行，却越来越难以真正运行。

三、真正让我破防的瞬间

折腾到后面，我已经开始怀疑是不是 API 本身出了问题。

于是我干脆打开 PowerShell，不经过任何项目代码，直接写了一个最简单的 API 请求。

只传模型名称和一句话。

运行。

SUCCESS。

整个请求只有十几个 Token，费用几乎可以忽略不计。

我看着终端里的成功提示，再看看那个被几百项测试、账户审计和权限校验层层包围的实验程序，实在有点绷不住。

当然，中途确实遇到过真实的服务商地区限制和政策拒绝，并不是之前所有报错都是程序制造的。

但在已经获得一个能够正常调用的 API Key 之后，实验程序却依然因为历史账户绑定、审核收据和各种保护机制拒绝运行。

这时候我才意识到：

我已经不再是在解决最开始的问题，而是在不断解决前几轮修改制造出来的新问题。

四、最后，我选择了重新开始

我决定不再修补原来的代码。

直接在相同项目目录里重新打开一个 Codex 对话。

没有冗长的历史背景，没有之前几十轮排查的过程，也不再强调那些层层叠加的保护要求。

只告诉它：

读取输入，调用一次模型，执行一次代码，保存结果。

保留必要的隔离执行和评价功能。

其他一切从简。

然后，新的脚本写好了。

我运行了一下。

成功了。

随后又完成了剩下的实验，终于得到了我最开始想要的结果。

前面花了那么长时间构建的庞大系统，最后竟然被一个重新开始的简单脚本替代了。

那一刻真的有一种哭笑不得的感觉。

五、这件事让我重新认识了 AI 编程

以前我觉得，使用 Codex 最重要的是把需求描述得足够详细，让它尽可能考虑所有边界情况。

但这次经历让我意识到，在一个持续很久的 AI 编程对话中，每一次临时决策都可能逐渐变成永久约束。

模型很擅长在现有架构上修补局部问题，却未必会主动推翻已经形成的设计。

用户不断报告问题，ChatGPT 不断提出修复方案，Codex 不断实现这些方案。三者配合得非常顺畅，却可能共同制造出一个越来越复杂的系统。

这和人类开发时不断打补丁、最终形成屎山没有本质区别，只不过 AI 把这个过程加速了很多倍。

当然，防御性代码和测试本身没有错。必要的安全边界仍然应该保留。

真正的问题是，**当连续几轮修改都没有让系统更接近目标时，也许就不应该继续修复，而应该重新审视需求，甚至直接推倒重来。**我觉得，这是目前AI都没有学会的一步，它只会根据问题一直改，而你需要判断这种操作是否能解决这个问题。

AI 能以惊人的速度帮你写出一座精密的堡垒。

但如果方向错了，它也能以同样惊人的速度，把你困在堡垒里面。
